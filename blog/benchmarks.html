ink vs the Field: An Honest Array Language Benchmark

Werner Almansa · May 2026 · ink v0.x (dev) · Apple M-series · macOS 14

ink is a new array programming language written in Zig. It speaks K—the dense, verb-oriented notation used by ngn/k, kdb+/q, and a constellation of open-source dialects. This post benchmarks ink against three well-established implementations across a spectrum of workloads: basic array verbs, heavy math, and a real-world quantitative-finance application.

Honest framing: ink is under active development. The numbers below show where ink stands today, not where it is headed. Several performance gaps are already understood and tracked.

The Contenders

ink

New array language written in Zig. K-dialect with first-class graphics. Compiles to a single ~4 MB binary. Tested build: zig-out/bin/ink.

ngn/k

Arthur Whitney–inspired K6 implementation by ngn. C source compiled to a tiny native binary. Legendary for startup speed and raw throughput. Installed at ~/.k/k.

goal

Goal is a K-inspired array language by Olivier Lauzanne, implemented in Go. Ships with a clean REPL and good stdlib. Binary at ~/Code/goal/goal.

q / kdb+

Kx Systems' commercial vector database language. The industry standard in HFT and quantitative finance. Free 32-bit version at ~/.kx/bin/q, run with -q (quiet mode).

BQN (CBQN) was planned but not found on this system. It would be a natural fit given CBQN's JIT-compiled performance; I'll add it in a follow-up post.

Methodology

All benchmarks run on an Apple M-series Mac (macOS 14, single core, no parallelism exploited by any runtime). Each backend is invoked as a fresh process per measurement—stdin for ink, ngn/k, and goal; stdin with a \ exit command for q. Results therefore include startup time and any JIT/warm-up cost. Five repetitions per cell; we report the median.

The benchmark runner is tool/bench_multi.py in the ink repo. Micro-benchmarks parameterise on N ∈ {1 k, 10 k, 100 k, 1 M}. Strategy benchmarks run entire script files end-to-end, three reps each.

Note on "net" times: Charts show net time—total median minus the baseline median at the same N. The baseline allocates a plain integer range (!N / til N), isolating operation cost from startup + allocation overhead. Where net is negative or zero (faster than baseline) we floor at 0.

Element-wise transcendentals (sqrt, exp, log), prefix scan, and inner product. These stress the floating-point dispatch path.

ngn/k once again returns near-zero net times for all math ops—its float pipeline is exceptionally tight. The picture for ink is split: exp and inner_product finish near-baseline (likely because the allocation cost dominates and the math itself is negligible), while sqrt, log, and +\ show 400–600 ms net overhead. The latter group all require producing a new N-element float array per element—the current implementation allocates individually rather than in a contiguous slab.

Real-World: Trading Strategy Parameter Sweeps

The true stress test: three quantitative trading strategies, each performing a parameter grid search over 1,249 days of AAPL price history. The strategies were designed to showcase K's strength—O(N) vectorised moving averages via prefix sums, boolean masking instead of branches, and zero explicit loops. These scripts are run end-to-end from a cold process.

Analysis

Where ink is competitive today

For small N (≤ 10 k) and aggregation verbs (sum, max) ink is already in the same bracket as goal and q once startup is accounted for. The absolute times— under 15 ms for most ops at N=10 k—are workable for interactive exploration.

The three performance gaps

1. Per-element allocation in element-wise ops

sqrt, log, and +\ all build a new float array element-by-element. The current Zig allocator path creates one allocation per element in the output; at N=1 M that is 1 M alloc/free calls. The fix is a map-in-place or map-to-preallocated-slab path. This alone should bring ink within 2–5× of ngn/k on transcendentals.

2. Dictionary-backed group (=)

ink's group implementation uses a general-purpose hash map that resizes and reallocates on every insert. ngn/k and goal use fixed-size compact representations for small key ranges. For the 100-bucket case at N=1 M, ink does ~1 M hash-map inserts with re-hash events; the expected fix is a two-pass counting approach (histogram + scatter), achieving O(N) with a single allocation.

3. Per-iteration frame cost in each (')

The strategy benchmarks reveal that ink's performance degrades roughly proportionally to the number of each-iterations rather than the total element count. The MA crossover has 300 iterations of an array operation on 1,249 elements: ~375 k total element-ops, yet takes 6.4 seconds—17 μs per iteration just in overhead. This overhead likely comes from closure capture, frame allocation, and garbage-pressure from intermediate arrays that are not freed eagerly.

The ngn/k ceiling

ngn/k is genuinely extraordinary: sub-4 ms for any micro-benchmark regardless of N up to 1 M, and 24–100 ms for full strategy sweeps that ink takes seconds to finish. This is what happens when a language runtime is hand-crafted in C by someone who has been optimising K interpreters for decades. It is an aspirational target, not a realistic near-term parity goal.

goal and q both sit in a reasonable middle ground—10–100 ms for large micro-benchmarks—and provide a more realistic competitive target for ink in the next few months.

What Comes Next

Near-term (next 1–2 months)

  • Slab-allocate output arrays for map-like verbs (sqrt, log, exp, scan)
  • Two-pass histogram group (=) for integer key ranges
  • Eager reclaim of intermediate values inside each (')
  • Re-run this benchmark suite as a regression guard in CI

Medium-term

  • SIMD paths for float reductions (sum, max, dot)
  • Add CBQN to the benchmark suite
  • Benchmark ink's graphics pipeline (the unique differentiator)
  • Publish updated numbers with each milestone
