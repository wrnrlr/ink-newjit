## Summary

X100 is the founding paper on **vectorized (a.k.a. batch-at-a-time) query execution**, the
middle ground between the two classic extremes:

- **Tuple-at-a-time (Volcano) interpreters** pay a virtual-call / dispatch cost for *every
  value*, defeating branch prediction and pipelining. Instruction count per useful op is huge.
- **Column-at-a-time (MonetDB MIL)** amortizes dispatch fully but materializes whole columns to
  RAM between every operator, so large columns spill out of cache and become bandwidth-bound.

X100 processes columns in **cache-resident vectors** (≈100–1000 values, sized to fit L1). One
interpreter dispatch drives a tight primitive loop over a whole vector, so:

- dispatch overhead is amortized over ~1000 elements (near the column-at-a-time win),
- but the working set stays in L1/L2, so no round-trip to DRAM between operators (avoids the
  MonetDB materialization cost),
- and the tight per-vector loops are **branch-free and auto-vectorizable**, keeping the
  superscalar pipeline full ("hyper-pipelining").

Primitives are monomorphic, compiled per (op, type) pair — e.g. `map_plus_double_col_double_col`
— which is exactly a jump table of specialized kernels. The paper shows order-of-magnitude
speedups over a traditional DBMS on TPC-H, and pins the wins to IPC and cache behavior with
hardware counters.

## Why it matters for Ink

This is the single most relevant paper to Ink's runtime. **Ink is already morally X100, not a
tuple-at-a-time interpreter**: the VM dispatches one verb over a whole array
(`vm.zig` `Apply2 → doApply → dispatch2`), and the kernels are monomorphized per type pair via a
comptime jump table (`src/primitive/verb/verbs.zig` `_N_N` / `makeDyad`, one specialization per
`(K, K)`). That is the X100 primitive design.

The gap is the **vector size**. X100 caps the batch at L1; Ink applies a verb to the *entire*
column:

- `helper.zig` `kernelVec2` does `N(R).init(vm.alloc, len)` — a full-length result allocation —
  then one scalar pass. A multi-MB column blows L1/L2, and a chain `a+b*c` allocates two full
  DRAM temporaries. This is precisely the MonetDB materialization cost X100 was built to remove.

The actionable X100 lesson for Ink is **chunk-and-fuse**: run pointwise verb chains over
cache-sized tiles (~1024 elems) with the whole tile kept in registers across the fused ops,
writing the result once. That raises arithmetic intensity (see `williams_2009_roofline.md`) and
is the design sketched in `doc/research/columnar-execution.md`. Ink's existing COW-in-place fast
path (kernelVec2 reuses an rc==1 input buffer) is a partial, per-op version of the same idea.
